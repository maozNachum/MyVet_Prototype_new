# מדיניות הקשחת התחברות והרשאות — MyVet

עודכן: 16.09.2026

מסמך זה מגדיר את מדיניות ה־Auth שנוספה במסגרת משימה 3.4. המדיניות נבדקה בסביבת Preview מבודדת; אין להסיק מכך שההגדרות הוחלו ב־Production.

## מדיניות מחייבת

- סיסמה חדשה או מאופסת: לפחות 12 תווים, אות גדולה, אות קטנה, מספר וסימן מיוחד.
- אין לשתף חשבונות. לכל עובד נדרש משתמש Supabase Auth אישי ורשומת `staff` פעילה השייכת למרפאה שלו.
- מנהל מרפאה (`clinic_admin`) ווטרינר (`vet`) חייבים להשלים TOTP ולקבל `aal2` לפני גישה למידע המרפאה.
- אחות ומזכירה רשאיות לעבוד ב־`aal1` בהתאם להרשאות התפקיד הקיימות. שינוי מדיניות זה דורש סקירת תפקידים ו־RLS.
- Access token תקף שעה. Refresh token rotation מופעל עם חלון שימוש חוזר של 10 שניות.
- משך סשן מרבי: 12 שעות; ניתוק לאחר שעה ללא פעילות.
- השבתת עובד, מחיקת שיוך צוות, שינוי תפקיד או שינוי משתמש Auth משויך מוחקים את הסשנים הפעילים שלו בצד השרת. RLS ממשיך לבדוק `is_active`, מרפאה, תפקיד ו־MFA בכל בקשה.
- שחזור סיסמה משתמש בקישור של Supabase Auth וחוזר למסך השחזור של MyVet. ההודעה למשתמש אינה חושפת אם כתובת מסוימת קיימת.

## הגנות נגד ניסיונות חוזרים

`supabase/config.toml` מגדיר את מדיניות הפיתוח המקומית: מגבלות שליחה, כניסה/הרשמה, אימות קודים ורענון token. בסביבת Hosted יש להגדיר ערכים מקבילים ב־Supabase Dashboard ולבחון אותם ב־Staging. CAPTCHA מומלץ לפני פתיחה מסחרית של הרשמה ציבורית, אך דורש מפתח ספק נפרד ולכן אינו מופעל בקוד ללא הגדרה מאושרת.

## תהליך ניהול חשבונות

1. חשבון צוות נוצר או מוזמן רק בידי גורם מורשה, ונקשר לרשומת `staff` אחת במרפאה הנכונה.
2. אין למסור סיסמה קבועה לעובד. משתמש חדש מגדיר סיסמה דרך תהליך Auth מאובטח.
3. מנהל או וטרינר נרשמים ל־TOTP בכניסה הראשונה וסורקים את קוד ה־QR ביישומון אימות.
4. בעת עזיבה או חסימת גישה מעדכנים `is_active = false`; אין להסתפק בהסתרת כפתור בממשק.
5. שינוי תפקיד מבטל סשנים קיימים. המשתמש חייב להתחבר מחדש ולהשלים MFA אם התפקיד החדש דורש זאת.
6. שחזור גישה לאחר אובדן גורם MFA מבוצע רק לאחר אימות זהות מתועד בידי בעל החשבון המורשה. אין להסיר MFA על סמך אימייל או שיחת טלפון בלבד.

## הגדרות Hosted שנבדקו ב־Preview

בסביבת ה־Preview הוגדרו ונשמרו:

- Password strength: מינימום 12 תווים ודרישת אות גדולה, אות קטנה, מספר וסימן מיוחד.
- Leaked password protection: מופעל. האפשרות תלויה בתוכנית Supabase Pro.
- TOTP MFA: הרשמה ואימות מופעלים.
- JWT expiry: שעה; refresh token rotation מופעלת.
- Session timebox: 12 שעות; inactivity timeout: שעה.
- Email confirmation ו־secure password change: מופעלים.
- Site URL ו־Redirect URLs: כתובות localhost של סביבת הבדיקה, כולל `/portal` ו־`/login?mode=recovery`.
- Rate limits: להתאים לערכי המאגר ולהקשיח לאחר בדיקות עומס ושיעור חסימות שווא.
- Single session per user: להפעיל אם זמין בתוכנית ולבדוק שאינו פוגע בעבודה המאושרת של הצוות.

אין להעתיק כתובות localhost ל־Production. אין לשמור סיסמאות, service role או recovery codes בריפו.

## תוצאות בדיקת הקבלה בענן — 16.09.2026

הבדיקה בוצעה בפרויקט Preview הקבוע `myvet-staging` (`fajwhkgafbjgnbgwsumt`); Production לא שונה.

- כל 26 מיגרציות ה־baseline הוחלו, ובדיקות הקטלוג, מטריצת התפקידים והקשחת Auth עברו.
- סיסמה חלשה נדחתה מסיבות `length` או `characters`, וסיסמה מוכרת כדולפת נדחתה במפורש עם הסיבה `pwned`; בדיקה אינה מסתפקת עוד בשגיאת Auth כללית.
- מסלולי יצירת הזמנה ושחזור סיסמה נבדקו באמצעות token מאומת: משתמש מוזמן הגדיר סיסמה והתחבר, ומשתמש שחזור קבע סיסמה חדשה והתחבר איתה.
- חשבון צוות סינתטי התחבר ב־`aal1`, לא ראה מידע רפואי, השלים TOTP ועבר ל־`aal2`.
- לאחר MFA החשבון ראה רק מרפאה ומטופל מה־tenant שלו; קריאה וכתיבה למרפאה הסינתטית השנייה נחסמו.
- השבתת העובד מחקה את ה־session הפעילה, ו־RLS חסם מיד JWT שכבר הונפק.
- כל שבע פונקציות ה־Edge החזירו 401 ללא JWT ו־`MFA_REQUIRED` ב־`aal1`; לאחר TOTP כולן עברו את מחסום ה־MFA.
- שבע פונקציות ה־Edge נפרסו מחדש ל־Preview בלבד מהקוד הנוכחי של `Full_Demo`, לאחר שנמצא פער גרסאות בסביבה.
- בדיקות Storage HTTP, ביטול גישה וקישורים חתומים עברו, וכן onboarding מלא לשתי מרפאות והזמנות צוות ובעלים.

בדיקת מסירת אימייל מלאה של הרשמה, הזמנה ושחזור לא הושלמה: ספק האימייל המובנה החזיר בעבר `over_email_send_rate_limit` (HTTP 429), ואין לפרויקט SMTP מאומת ותיבת קבלה ייעודית. נדרש להריץ בדיקת מסירה חוזרת בסביבת Staging קבועה עם SMTP מאומת לפני Production. בדיקת ה־token, שינוי הסיסמה והכניסה לאחר הזמנה ושחזור כן עברה.

## בדיקות קבלה נדרשות

- סיסמה חלשה וסיסמה ידועה כדולפת נדחות ב־Staging.
- מנהל ווטרינר ב־`aal1` יכולים להגיע רק למסך MFA ואינם יכולים לקרוא או לשנות נתוני מרפאה דרך API/RPC.
- לאחר אימות TOTP מתקבל `aal2` והגישה המורשית פועלת.
- אחות ומזכירה ממשיכות לקבל רק את הרשאות התפקיד שלהן.
- השבתת עובד, מחיקת שיוך ושינוי תפקיד מבטלים refreshable sessions ומונעים בקשות נוספות.
- איפוס סיסמה אינו חושף קיום חשבון, אינו משנה tenant ואינו מקשר משתמש לבעלים או למרפאה אחרת.
- הזמנה, כניסה ראשונה, שחזור, revoke ושינוי תפקיד נבדקים עם שתי מרפאות סינתטיות.

`npm run test:supabase-baseline` מריץ במסד מקומי נקי גם את בדיקת ה־RLS והסשנים וגם מסע Auth אמיתי: דחיית סיסמה חלשה, כניסת מנהל ב־`aal1`, רישום ואימות TOTP, מעבר ל־`aal2`, חסימת מידע לפני MFA וביטול גישה וסשן לאחר השבתה. חסימת סיסמה דולפת הוכחה ב־Preview Hosted. מסירת אימייל הזמנה ושחזור מלאה עדיין מחייבת Staging עם SMTP מאומת ואינה ניתנת להוכחה ב־Supabase Local בלבד.

## אחריות תפעולית

- בעל חשבון Supabase המאושר אחראי להגדרות Hosted, MFA לחשבונות ניהול, גישה ל־Dashboard ושמירת ראיות הבדיקה.
- אחראי האבטחה של MyVet מאשר שינויי מדיניות, בודק Advisors ומתעד חריגות.
- פריסה ל־Production מתבצעת רק לפי `docs/PRODUCTION_RUNBOOK_HE.md` ולאחר PASS מלא ב־Staging.
