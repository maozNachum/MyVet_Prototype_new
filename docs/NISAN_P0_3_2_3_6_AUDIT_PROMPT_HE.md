## סולם הסטטוסים

לכל תנאי קבלה החזר אחד מהסטטוסים הבאים:

- `PASS` - קיימת ראיה ישירה, והבדיקה הרלוונטית עברה.
- `PARTIAL` - קיים מימוש או מסמך, אך חלק מתנאי הקבלה לא אומתו.
- `FAIL` - קיימת ראיה שהתנאי אינו מתקיים.
- `BLOCKED` - אי אפשר לאמת ללא סביבת בדיקה, גישה, החלטה עסקית או גורם משפטי.
- `NOT IMPLEMENTED` - לא נמצא מימוש או תוצר מתאים.

יש להפריד בכל מקום בין:

1. קיים בקוד או במסמך.
2. נבדק מקומית.
3. נבדק בסביבת Supabase מבודדת.
4. הוחל ב-Production.
5. אושר עסקית או משפטית.

## חלק א - ביקורת P0-3.2 / F-023

### הבעיה שאמורה להיפתר

`claim_owner_profile()` לא אמורה לבחור אוטומטית בעלים כאשר אותו אימייל מאומת מופיע ביותר ממרפאה אחת. הקישור חייב להתבצע רק כאשר קיימת התאמה אחת, יחידה ומוכחת. במקרה של אפס התאמות או מספר התאמות אסור לשנות שום רשומה.

### מיפוי חובה

אתר ותעד:

- כל הגדרה של `claim_owner_profile()` בכל קובצי ה-Migration.
- איזו הגדרה היא האחרונה לפי סדר המיגרציות.
- כל קריאה לפונקציה ב-Frontend, בשירותים, ב-Edge Functions ובבדיקות.
- Policies, ‏Grants, ‏Triggers או Functions שמשפיעים על `owners`, ‏`auth_user_id`, אימייל ושיוך למרפאה.
- קוד Frontend שמציג למשתמש הצלחה או שגיאה בעת Claim.
- Tests קיימים הנוגעים ל-Owner signup, Claim, שתי מרפאות, RLS או כפילויות.
- commits או שינויים מקומיים שניסן יצר עבור 3.2.

אל תניח ששמות טבלאות, עמודות או חתימות פונקציה נשארו כפי שהיו בדוח. אמת אותם מול המאגר הנוכחי.

### בדיקות סטטיות נדרשות

בדוק מהקוד וה-SQL:

- שהפונקציה אינה מקבלת אימייל, `clinic_id`, ‏`owner_id` או תפקיד מה-Frontend לצורך החלטת הרשאה.
- שהאימייל המאומת נלקח מזהות שרתית או JWT מאומת, ולא מ-`user_metadata` הניתן לעריכת המשתמש.
- שהפונקציה מקשרת רק כאשר מספר ההתאמות הוא בדיוק אחת.
- שבמקרה של אפס התאמות או יותר מהתאמה אחת לא מתבצע `UPDATE` חלקי.
- שהפעולה אטומית ו-fail-closed.
- שקיים `search_path` בטוח אם הפונקציה היא `SECURITY DEFINER`.
- שאין הרשאת `EXECUTE` רחבה ל-`anon` או ל-`PUBLIC`.
- שה-Grants וה-RLS אינם מאפשרים לעקוף את הפונקציה באמצעות כתיבה ישירה.
- שהודעת השגיאה למשתמש ברורה ואינה חושפת פרטי מרפאה או בעלים אחרים.

### תרחישי קבלה נדרשים

חפש ראיות קיימות או הרץ בדיקות מקומיות בטוחות בלבד עבור:

1. התאמה יחידה ומוכחת - הקישור מצליח פעם אחת.
2. אפס התאמות - אין שינוי נתונים.
3. אותו אימייל בשתי מרפאות - אין שינוי נתונים ומוחזרת שגיאה בטוחה.
4. ניסיון לשלוח `clinic_id` ידני מה-Frontend - אינו משפיע על הבחירה.
5. ניסיון חוזר לאחר הצלחה - אינו יוצר שיוך כפול ואינו פוגע ברשומה.
6. שתי בקשות מקבילות - אינן מקשרות שתי רשומות ואינן יוצרות מצב חלקי.
7. משתמש ממרפאה אחרת - אינו מקבל Metadata או מידע על התאמות אחרות.
8. משתמש אנונימי - אינו יכול להפעיל את הפעולה.

אם התרחישים אינם קיימים כבדיקות, אל תכתוב שהם עברו. ציין בדיוק אילו בדיקות חסרות.

### פקודות אימות מותרות

לאחר בדיקת `package.json`, הרץ את הפקודות הרלוונטיות שקיימות בו, לכל הפחות כאשר הסביבה מאפשרת:

- `npm run test:vetbot`
- `npm run test:ai-data-security`
- `npm run test:ai-data-local`
- `npm run build`
- `git diff --check`

אם Docker/Supabase Local אינם זמינים, ציין אילו בדיקות לא הורצו ומדוע. אין להתקין כלי חדש רק לצורך הביקורת.

### תוצאת 3.2 הנדרשת בדוח
